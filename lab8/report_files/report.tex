\section{Aim, deliverables, and build}
This lab repeats the process experiment from Lab 7 inside xv6 and then
uses two pipes to exchange a byte between a parent and a child. The aim is
to connect the shell-level behavior observed in Lab 7 to the smaller xv6
system-call interface: \texttt{fork} creates a child, \texttt{exec}
replaces its program, \texttt{wait} reaps it, and \texttt{read}/\texttt{write}
move bytes through pipes.

I added \texttt{user/run.c} and \texttt{user/pingpong.c} to the integrated
\texttt{os/xv6-riscv} tree. Both names were added to the Makefile's
\texttt{UPROGS} list, so \texttt{mkfs} includes their binaries in
\texttt{fs.img}. Matching source files and the Makefile are in
\texttt{lab8/code/}; this report's source is in
\texttt{lab8/report\_files/}. I used the local RISC-V compiler and QEMU
on 26 October 2026. The relevant build and launch commands were:

\begin{lstlisting}
$ make clean
$ make fs.img
... user/run.c ... user/pingpong.c ...
nmeta 47 (boot, super, log blocks 31, inode blocks 13,
          bitmap blocks 1) blocks 1953 total 2000
$ make qemu
xv6 kernel is booting
init: starting sh
$
\end{lstlisting}

The compiler completed with xv6's \texttt{-Wall -Werror} settings. For
the requested \texttt{ls} and nonexistent-program experiments, I
temporarily changed \texttt{user/run.c}, rebuilt the user binary and disk
image, and booted QEMU again. I restored the submitted \texttt{echo}
version and forced a final rebuild of both \texttt{run} and
\texttt{fs.img}. A final boot verified the restored image.

The artifacts serve different purposes. The two C files are the actual
xv6 user programs. The Makefile is needed to place their binaries in the
image; copying a C file into \texttt{user/} alone would not make it
available at the xv6 shell. The \texttt{notes.md} file preserves the
short Observe answers, while this report explains the call sequence and
the evidence in more detail. Each QEMU run began from the shell prompt
shown in the transcripts. The PIDs are from those particular boots and
are observations, not fixed values required by the programs.

\section{Part 1: a program starts another program}
\subsection{How the process moves through the three calls}
The final \texttt{run.c} first prints the parent's PID. The return value
of \texttt{fork()} distinguishes the two paths: zero in the child and
the child's PID in the parent. The child builds an argument vector ending
in a null pointer and executes \texttt{echo}. The parent calls
\texttt{wait(\&status)} and prints the status after the child has ended.
The core of the implementation is:

\begin{lstlisting}[language=C]
int pid = fork();
if(pid == 0){
  char *args[] = { "echo", "hello", "from", "the", "child", 0 };
  exec("echo", args);
  printf("exec failed\n");
  exit(1);
}
int status;
wait(&status);
printf("parent: child %d ended with status %d\n", pid, status);
\end{lstlisting}

Successful \texttt{exec} replaces the child process's address space. It
does not create a second child and does not return to the error print in
\texttt{run.c}. The child keeps its PID while the new \texttt{echo}
program writes the supplied words. The parent remains blocked in
\texttt{wait} until that program exits.

\begin{lstlisting}
$ run
parent: my pid is 3
child: my pid is 4
hello from the child
parent: child 4 ended with status 0
\end{lstlisting}

The observed PID 4 is the child created by PID 3. The words
\texttt{hello from the child} come from \texttt{echo}, not from a print
statement in \texttt{run.c}. The child's successful exit produced status
0, which the parent reported after \texttt{wait} returned.

\subsection{A failed exec and its exit status}
For the third run, the child attempted
\texttt{exec("nosuchprog", args)}. There was no matching executable in
the image, so \texttt{exec} returned to \texttt{run.c}. The error print
and \texttt{exit(1)} then executed:

\begin{lstlisting}
$ run
parent: my pid is 3
child: my pid is 4
exec failed
parent: child 4 ended with status 1
\end{lstlisting}

The status is 1 because xv6's example explicitly calls \texttt{exit(1)}
after failed \texttt{exec}. Lab 7's POSIX version calls
\texttt{exit(127)} after failed \texttt{execlp}, so its parent reports
127. The different values are choices made by the example programs;
\texttt{exec} itself does not assign them.

only the child's program is replaced.

\section{Part 2: the pingpong exchange}
\subsection{Why there are two pipes}
\texttt{pingpong.c} creates both pipes before \texttt{fork}, so the
parent and child inherit descriptors for both. A pipe has a read end
and a write end and carries bytes from the latter to the former. One
pipe carries the request from parent to child; the other carries the
reply in the reverse direction. A single pipe would not give the two
messages separate routes: both processes could compete to read the
same byte, including a process reading its own write.

\begin{center}
\begin{tabular}{>{\raggedright\arraybackslash}p{2.2cm}
                >{\raggedright\arraybackslash}p{4.8cm}
                >{\raggedright\arraybackslash}p{4.8cm}}
\toprule
Process & Descriptors it keeps & Descriptors it closes \\
\midrule
Parent & \texttt{p2c[1]} to send; \texttt{c2p[0]} to receive &
  \texttt{p2c[0]}, \texttt{c2p[1]} \\
Child & \texttt{p2c[0]} to receive; \texttt{c2p[1]} to send &
  \texttt{p2c[1]}, \texttt{c2p[0]} \\
\bottomrule
\end{tabular}
\end{center}

Each process closes its retained ends after use as well. This avoids
unnecessary open descriptors and lets readers observe end-of-file if
their peer exits without sending data. The program checks the return
values of \texttt{pipe}, \texttt{fork}, \texttt{read}, and \texttt{write}
and reports a short error message if one fails.

\clearpage
\subsection{What orders ping before pong}
The parent begins with a byte \texttt{'x'} and writes exactly one byte
to \texttt{p2c[1]}. The child reads it from \texttt{p2c[0]}, prints
\texttt{received ping}, then writes that same byte to
\texttt{c2p[1]}. The parent calls \texttt{read(c2p[0], \&b, 1)} before
printing \texttt{received pong}. If the child has not replied, this
\texttt{read} blocks. The order follows from the byte exchange; there
is no timer or separate sleep call.

\begin{lstlisting}[language=C]
// Parent: send request, then wait for the reply byte.
write(p2c[1], &b, 1);
close(p2c[1]);
read(c2p[0], &b, 1);
printf("%d: received pong\n", getpid());
wait(&status);

// Child: receive request, then return the same byte.
read(p2c[0], &b, 1);
printf("%d: received ping\n", getpid());
write(c2p[1], &b, 1);
\end{lstlisting}

These excerpts show the successful path; the submitted C source also
checks each call's result and closes descriptors on error. The
\texttt{wait(\&status)} after the parent's print reaps the child. It
does not make the parent wait for the reply: that happens at
\texttt{read(c2p[0], \&b, 1)}.

\begin{lstlisting}
$ pingpong
6: received ping
5: received pong
$ pingpong
8: received ping
7: received pong
\end{lstlisting}

The PIDs changed between runs because each invocation created a new
parent and child. In both runs, the child printed first and the parent
printed after reading the reply. The byte itself is not displayed;
the messages identify which side has completed its read.

\section{Verification and conclusion}
I tested the final \texttt{run} and \texttt{pingpong} programs after
restoring the \texttt{echo} source and forcing a fresh image build. The
final QEMU run again printed \texttt{hello from the child}, a status of
0, and two ping-before-pong pairs. The source copies in
\texttt{lab8/code/} matched the corresponding xv6 files byte for byte.

The experiments show that xv6 implements the same basic process
lifecycle as the POSIX example: a child is created, replaced with a new
program, and reaped. A failed \texttt{exec} returns to the child and
allows it to choose an error status. Two directed pipes and a blocking
read provide the request-and-reply ordering in \texttt{pingpong}.
